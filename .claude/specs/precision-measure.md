# 추출 정확도 측정 (2,055건 재측정, 다른 컴퓨터 실행용)

작성: 2026-10-21. 이 문서를 실행할 사람은 다른 컴퓨터에서 맥락 없이 시작하는 Claude 세션입니다. 지난 대화 내용을 몰라도 이 문서만으로 끝까지 할 수 있게 썼습니다.

## 1. 목표

이전 측정(2026-10-20, 채움률 보강)은 **값을 찾았는지(채움률)**만 쟀습니다. 그래서 찾은 값이 틀린 경우가 성공으로 집계됐습니다. 예를 들면 빈 서식 `20  년  월  일`, "경력사항은 5년이내"를 실적 인정기간으로 잡은 경우가 그렇습니다.

이번 측정은 같은 2,055건으로 다음 두 가지를 잽니다.

1. **"공고정보 검토" 건수 분포.** 앱이 공고마다 표시하는 확인 필요 건수가 공고당 몇 건인지, 항목별·사유별(못 찾음/충돌/여러 값)로 집계합니다.
2. **오탐 신호.** 값은 찾았지만 틀렸을 가능성이 높은 경우를 신호별로 셉니다. 각 신호마다 예시 공고를 함께 뽑습니다.

결과를 보고 사용자와 함께 규칙 수정 우선순위를 정하는 것이 이 작업의 끝입니다. **이 측정 작업에서 규칙(`default-rules.json`)과 코어 코드는 고치지 않습니다.**

## 3. 하네스 정비 (실행하는 Claude가 할 일)

`scripts/*.mjs`와 `extract.test.ts`에는 원래 컴퓨터의 절대경로가 하드코딩되어 있습니다. 바꿔야 할 값은 세 가지입니다.
- `ROOT`: 원래 `.../research/recent` 경로입니다.
- 저장소 경로: 원래 `C:/workspace/bidMate`입니다.
- `vitest.config.mjs`의 `root`: 원래 `.../research` 경로입니다.

이 세 값을 환경변수 `MEASURE_ROOT`(= `<M>/recent`)와 `BIDMATE_REPO`(= 저장소 경로)로 바꿉니다. 하네스는 `<M>/scripts/`에 둔 채로 고치고, 저장소에는 넣지 않습니다.

### 3-1. 추출 하네스 (`extract.test.ts`) 수정
지금은 `notice`·`extraction`의 일부 필드만 저장합니다. 아래 세 가지를 바꿉니다.
- **전체 저장:** `store`에 쓰인 `notice.json`과 `extraction.json`을 **전체 그대로** 저장합니다. 검토 건수 계산에 Notice 전체가 필요하기 때문입니다.
- **출력 폴더:** 결과를 새 폴더 `<M>/recent/extract_v112/`에 씁니다. 기존 `extract/`는 덮어쓰지 않고 비교용으로 남깁니다.
- **텍스트 폴더:** 문서 텍스트는 `<M>/recent/text_v112/<공고번호>/`에 씁니다.

나머지 동작은 그대로 둡니다.
- `category !== 'other'`인 공고만 대상으로 합니다.
- 다운로드와 API는 로컬 파일로 대체합니다.
- `html: undefined`로 둡니다.
- 출력 파일이 이미 있으면 건너뜁니다. 그래서 중단돼도 다시 실행하면 이어서 돕니다.

실행 명령은 아래와 같습니다.

```
cd <M>
set MEASURE_ROOT=<M>/recent
set BIDMATE_REPO=<저장소>
<저장소>/node_modules/.bin/vitest run --config vitest.config.mjs
```

- 2,055건에 수 시간이 걸립니다. 백그라운드로 실행합니다.
- 진행 로그는 10건마다 `extracted N`으로 나옵니다.
- 특정 공고만 다시 돌릴 때는 `ONLY=번호1,번호2`를 씁니다.

### 3-2. HTML 없는 항목 처리
- 측정에서는 나라장터 상세 화면(HTML)을 쓰지 않습니다.
- 그래서 화면값으로만 채워지는 항목은 앱보다 확인 필요가 많이 나옵니다.
- **항목별 집계에서 이런 항목을 따로 표시합니다.** 추출 결과에서 `notice.json`의 해당 필드 `source`가 HTML 계열이거나, 항목이 문서 추출 대상(`EXTRACTION_KEYS`와 `extras.projectPeriod`·`proposalPeriod`·`proposalEvalAt`)이 아닌지로 판정합니다.
- 총 건수는 두 가지로 냅니다: "문서 추출 항목만"과 "전체".

## 4. 측정 스크립트 (`<M>/scripts/measure4.mts`, 새로 작성)

- **코드 재사용:** 앱 코드를 import해서 앱과 같은 방식으로 계산합니다. 판정 로직을 새로 짜지 않습니다. 실행은 3-1과 같은 vitest 설정에 `scripts/measure4.test.ts`로 두는 방식이 가장 간단합니다(TS import 때문).
- **입력:** `extract_v112/*.json`과 `notices.json`(기관과 낙찰방법).
- **출력:** `<M>/recent/measure4.md`와 `<M>/recent/measure4.samples.json`.
- **그룹 분리:** 모든 표는 **협상 / 그외** 그룹으로 나눕니다. 그룹 판정은 `measure3.mjs`와 같습니다: `sucsfbidMthdNm`, `cntrctCnclsMthdNm`, `awardMethod`에 "협상"이 있으면 협상 그룹입니다.
- **기관별 수치:** 각 수치 옆에 기관별(축평원/행안부/KOICA) 수치를 함께 씁니다.

### 4-1. 공고정보 검토 건수 분포
- **계산 방식:** `src/core/extraction/review-rows.ts`의 `pendingLeafKeys(notice, extraction)`와 `leafReviewState`를 그대로 사용합니다. 앱의 "공고정보 검토" 숫자와 같은 계산입니다.
- **표 A — 공고당 건수 분포:**
  - 0, 1, 2, 3, 4, 5~7, 8건 이상 구간별 공고 수와 비율을 냅니다.
  - 문서 추출 항목만 / 전체, 두 기준으로 냅니다.
- **표 B — 항목별:**
  - 항목마다 확인 필요 건수를 사유별로 나눕니다: 못 찾음(not_found) / 충돌(conflict) / 여러 값(multi) / 기타.
  - 항목은 `REVIEW_LEAF_KEYS`의 16개이고, 라벨은 `REVIEW_LABEL`을 씁니다.
  - 해당 없음(`reason: 'not_applicable'`)으로 처리된 건수도 `naKind`별로 함께 적습니다.
- **표 C — 많이 나오는 공고:** 확인 필요가 가장 많은 공고 30건을 뽑습니다. 열은 공고번호, 공고명, 기관, 건수, 항목 목록입니다.

### 4-2. 오탐 신호
공고별·항목별로 아래 신호를 검사합니다. 신호마다 다음 두 가지를 냅니다.
- 해당 건수(협상/그외 × 기관)
- **예시 10건**(시드 고정 무작위): 공고번호, 항목, 값, 근거 줄 원문

검사에는 다음 필드를 씁니다.
- `extraction.json`의 `items`·`extras`에 있는 `value`, `evidence.evidence`(근거 문장), `candidates`
- 충돌 항목의 `candidates`

| 신호 | 조건 | 의심하는 문제 |
|---|---|---|
| S1 형식만 다른 충돌 | 충돌 항목의 후보 값들을 공백·구두점·괄호를 지우고 비교했을 때 같거나 한쪽이 다른 쪽을 포함함. 기간은 `src/core/model/period.ts`의 `periodKey`로 비교 | 같은 값을 다른 값으로 취급 |
| S2 빈 서식 값 | 값 또는 근거에 숫자 없는 날짜 틀이 있음 (`년\s*월\s*일`, `.\s*.\s*.\s*~`, `20\s+년`) | 서식·양식에서 잡음 |
| S3 서식 구간 근거 | 근거 문장 또는 그 문서 위치 주변에 `서식`, `양식`, `계약서(안)`, `[별지`, `작성예시`, `(예시)`가 있음 | 서식 구간 강등 누락 |
| S4 실적 문맥 오탐 | `performancePeriod`·`performanceMinAmount`·`performanceCondition`의 근거에 `경력`, `하도급`, `하수급`, `공동수급`, `지분`, `구성원`, `투입인력`, `기술자`가 있음 | 실적이 아닌 문장에서 잡음 |
| S5 점수 범위 이상 | 배점 항목(`credibilityScore`·`managementScore`·`performanceScore`) 값이 0 이하, 100 초과, 또는 소수 둘째 자리 이상. 세 배점 합이 100 초과 | 표 셀 오인식 |
| S6 해당 없음인데 문서에 정량 근거 | 항목이 not_applicable인데, 같은 공고 텍스트(`text_v112/`)에 그 항목의 배점 키워드(대외신인도·신용평가·경영상태·수행실적)와 숫자+`점`이 같은 줄에 있음 | 해당 없음 과적용 |
| S7 못 찾음인데 문서에 키워드 | not_found인데, 같은 공고 텍스트에 그 항목의 대표 키워드가 있음. 키워드는 `default-rules.json`의 해당 규칙 `anchors`/동의어를 그대로 사용 | 재현율 누락 후보 (오탐 아님, 참고용) |
| S8 문서 간 값 불일치 | 같은 항목에서 공고문(notice)과 제안요청서(rfp) 후보 값이 다르고, 최종값이 verified | 우선순위로 묻힌 실제 충돌 |

- S3·S6·S7처럼 텍스트를 봐야 하는 신호는 근거의 `location`(줄 번호)으로 `text_v112/<공고번호>/` 파일의 앞뒤 5줄을 봅니다.
- 위치 형식은 `measure3.mjs`의 `textLines`와 근거 표시 방식을 참고해서 확인합니다.
- 위치를 찾지 못하면 신호를 판정하지 않고 "위치 불명" 건수로 셉니다.
